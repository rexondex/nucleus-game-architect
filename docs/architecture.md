# 코드 아키텍처

## 확정 스택

- TypeScript + Vite
- React: DOM UI와 화면 조립
- React Three Fiber: 3D 세계의 시각 투영
- Three.js는 R3F가 사용하는 렌더링 기반 라이브러리다. 별도의 렌더 루프를 만들지 않는다.

## 큰 폴더 네 개

게임 소스는 `src/` 바로 아래 네 개의 책임 영역으로 나눈다. 이 네 폴더가 게임 구현의 최상위 모듈이다.

| 영역 | 담당 책임 | 금지 책임 |
|---|---|---|
| `src/01_nucleus-core/` | 권위 장부, 게임 설정·콘텐츠 정의, 상태 모델과 그래픽 독립 시뮬레이션 | UI/R3F, 브라우저 저장소, 화면 표시 |
| `src/02_api-controller/` | 코어를 감싸는 공개 게임 컨트롤러, 명령 검증·전달과 읽기 질의 | DOM·3D 렌더링, 화면 상태 |
| `src/03_graphics-projection/` | R3F 컴포넌트, 장면, 캐릭터·오브젝트 투영 | 장부 직접 접근, DOM UI, 게임 규칙 소유 |
| `src/04_ui-interface/` | React DOM, 버튼·패널, 화면 구성 및 API 명령 입력 | 장부 직접 접근, Three.js 객체 생성 |

숫자가 작을수록 권위와 우선순위가 높다. `01`은 게임의 진실을 소유하는 코어이고, 숫자가 커질수록 바깥의 접근·표현 계층이다. 폴더명만 읽어도 책임과 방향을 파악하도록 역할을 영문 이름으로 함께 적는다.

`src/main.tsx`는 앱 마운트와 전역 스타일만 담당하는 부트스트랩 예외다. 콘텐츠나 게임 기능을 이 파일에 넣지 않는다.

```text
                   ┌──────────────┐
                   │ src/01_nucleus-core/ │  장부 + 시뮬레이션 규칙
                   └──────▲───────┘
                          │ 유일한 코어 접근
                   ┌──────┴──────┐
                   │  src/02_api-controller/   │  게임 컨트롤러 / 공개 API
                   └───▲─────▲───┘
                 명령·읽기   읽기/입력
              ┌───────┘     └────────┐
        ┌─────┴────────┐       ┌──────┴─────┐
        │ src/03_graphics-projection/│       │  src/04_ui-interface/   │
        │ 3D 투영/입력 │◄──────│ DOM 화면   │
        └──────────────┘ 화면 조립 시 포함

src/main.tsx → src/04_ui-interface/ 화면 진입점
```

허용 의존 방향은 다음과 같다.

```text
02_api-controller      -> 01_nucleus-core
03_graphics-projection -> (전달받은 읽기 전용 props; 필요 시 02 API 타입만)
04_ui-interface        -> 02_api-controller, 03_graphics-projection
01_nucleus-core        -> 외부 API/UI/렌더링 영역 없음
```

`03_graphics-projection`와 `04_ui-interface`는 각각 같은 API에 연결된다. 화면 조립을 위해 UI가 그래픽 컴포넌트를 포함할 수 있지만, 그래픽 계층은 UI에 의존하지 않는다. `.dependency-cruiser.cjs`가 코어 우회와 순환 의존을 차단한다.

## 핵심 데이터 흐름

```text
키보드·버튼·3D 상호작용
          ↓ 명령
       src/02_api-controller/ 공개 컨트롤러
          ↓ 검증된 시뮬레이션 명령
       src/01_nucleus-core/ 장부 갱신
          ↓ 읽기 전용 스냅샷
       UI / 3D 투영 갱신
```

- 장부는 게임 설정, 콘텐츠 정의, 현재 플레이 상태, 과거 변경 이력, 미래 예약을 포함하는 유일한 권위 모델이다.
- UI와 R3F 객체는 장부에서 만든 인스턴스/투영이다. 영구 게임 상태를 React/R3F 로컬 상태에 중복 저장하지 않는다.
- 화면 행동은 장부 객체를 수정하지 않고 API에 명령을 보낸다. 게임 규칙은 `01_nucleus-core`에서 렌더러 없이 실행된다.
- `src/01_nucleus-core/ledger.ts`는 구름섬 설정, 오브젝트, 캐릭터, 의상, 수집품, 역할, 플레이 상태와 시간 예약을 가진 코어 구현이다. `src/02_api-controller/game-api.ts`는 코어를 감싸는 공개 진입점이다.
- 현재 R3F 장면은 API가 읽은 발견 수를 props로 받아 수집 흔적을 투영하는 프리미티브 단계다. 게임 데이터와 아트 에셋은 추가 확장 대상이다.

## 시간과 미래 행동

- 이벤트 기록은 장부 기록 시각 `recordedAt`과 세계 효력 시각 `effectiveAt`을 구별한다.
- 예약은 `scheduled`, `applied`, `cancelled` 상태를 가지며 게임 시간 진행 시 효력 시각이 지난 항목을 적용한다.
- API는 미래 섬 이벤트를 예약하거나 예약을 취소할 수 있다.
- 현재 이력은 모든 변경을 완전 재생해 과거의 임의 시점 상태를 복구하는 수준은 아니다. 이력 재생/되감기와 영구 저장은 후속 구현이다.

## 네 영역의 파일 배치

```text
src/
├── 01_nucleus-core/         # 권위 데이터 장부와 시뮬레이션
├── 02_api-controller/       # 공개 명령/질의 인터페이스
├── 03_graphics-projection/  # 장부 상태의 R3F 시각 투영
├── 04_ui-interface/         # 플레이어 조작 및 정보 UI
└── main.tsx                 # 웹 진입점 예외
```

큰 이미지·모델·오디오는 장부에 바이너리로 넣지 않는다. 안정적인 ID와 메타데이터를 장부가 소유하고 에셋 파일을 참조한다. 저장과 온라인 서버 기능은 나중에도 API 뒤의 명시적 어댑터로 연결한다.

## 기존 패턴과 용어

- 전체 구조의 프로젝트 표현은 **장부를 권위 상태로 삼는 헤드리스 시뮬레이션**이다.
- `headless/domain-centric`은 게임 규칙을 표시 계층에서 분리하는 측면을 설명한다.
- `CQRS-inspired`는 API의 명령 경로와 UI/3D의 읽기 투영을 나누는 측면을 설명한다.
- 과거 이력에서 상태를 재구성하도록 확장하면 event-sourcing에 가까워진다. 현재 코어는 예약 및 이력의 초기 구현이며 완전한 재생 엔진은 아니다.
- “세포핵”, “블랙홀/홀로그램”은 이 원칙을 설명하는 프로젝트 은유이며 정식 엔진 표준 용어라고 주장하지 않는다.

## 코어 게임 체크

- `src/02_api-controller/verification/game-check.test.ts`는 게임을 새로 생성하고 API 명령만으로 여러 플레이 흐름을 시뮬레이션한다. nucleus 내부 함수나 장부 저장소를 직접 만지지 않는다.
- `npm run check:game`으로 단독 실행하고, `npm run check`와 `npm run build`에서도 자동 실행한다.
- Node 내장 테스트 러너와 TypeScript 타입 제거 기능을 사용하므로 Node 22.6 이상이 필요하다.
- 현재 자동 검사 범위는 시작 콘텐츠 참조, 스냅샷 분리, 장비, 탐험·기운·보상·수집, 휴식, 오브젝트 상호작용, 이름 변경, 과거 행동 이력, 미래 일정 예약·취소·정시 1회 적용이다.
- 과거 임의 시점 복원, 영구 저장/재접속, 네트워크·권한, 외부 링크 실제 열기, 브라우저와 3D 렌더링은 아직 구현/검증 범위가 아니다.

## 코어 라이브 뷰어

- `src/02_api-controller/verification/game-viewer.ts`는 별도 게임 인스턴스를 만들고 공개 API만 사용해 세계 시간을 계속 진행한다. 매 tick마다 설정, 세계·플레이어 상태, 보유·장착·수집 목록, 전체 예약 상태와 최근 이력을 출력한다.
- `npm run view:game`으로 시작한다. 기본 속도는 실제 1초마다 게임 1시간이다. `pause`, `resume`, `speed <밀리초>`로 시계를 제어하고, `explore`, `rest`, `equip`, `interact`, `rename`, `schedule`, `cancel`, `time` 명령으로 플레이를 조작한다.
- `events`는 누적 이력 전체를, `dump`는 현재 장부 JSON 전체를 보여준다. `Ctrl+C` 또는 `quit`으로 뷰어를 종료한다.
- `npm run view:game -- --ticks=2 --tick-ms=50`은 두 tick만 출력하는 종료형 smoke 실행이다. 기본 실행은 중지할 때까지 계속 돈다.
- 라이브 뷰어와 자동 테스트 모두 Node 22.6 이상의 내장 TypeScript 타입 제거 기능을 사용한다.

## 계정별 저장 위치와 배포 모드

현재 프로토타입의 장부는 메모리에서만 유지된다. 웹 배포 전에 영구 저장 어댑터가 필요하다. 물리 저장 위치는 환경 설정이 선택하되, 장부 API와 핵의 논리 스키마는 유지한다.

| 실행 모드 | 권장 장부 저장 위치 | 장부 선택 키 |
|---|---|---|
| 브라우저 싱글플레이 | 브라우저 IndexedDB. 논리 DB 이름은 `virtual-forest`, object store는 `player-ledgers` 같은 고정 이름을 사용한다. | 로컬 프로필 ID + 캐릭터 슬롯 ID |
| 온라인 계정 플레이 | 서버 DB의 `player_ledgers` 행과 필요 시 연결된 append-only 이벤트 행 | 인증 미들웨어가 검증한 `account_id` + 슬롯 ID |

웹 페이지는 사용자의 임의 로컬 디스크 경로에 접근할 수 없으므로 싱글플레이의 기본 장부 경로를 `D:\...` 같은 파일 경로로 지정하지 않는다. IndexedDB는 사이트 origin에 종속되며 브라우저가 관리한다. 사용자가 명시적으로 폴더 선택 권한을 주는 파일 API는 백업/내보내기 같은 선택 기능에만 고려한다. IndexedDB는 같은 origin의 브라우저 저장소이며 서버 DB 동기화 기능 자체를 제공하지 않는다. [MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB), [MDN File System API](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API)

`.env`에는 환경별 모드, 공개 API 주소, 서버 전용 DB 연결 설정을 둔다. **계정별 플레이 데이터나 실제 디스크상 유저별 파일 경로를 `.env`에 열거하지 않는다.** 사용자가 많아져도 서버가 인증된 `account_id`로 DB 행을 선택한다. Vite의 `VITE_` 접두 환경값은 클라이언트 번들에서 읽을 수 있으므로 공개 API 주소 같은 비밀이 아닌 값만 둔다. DB 비밀번호와 서버 비밀은 서버 프로세스 환경에만 둔다. [Vite environment variables](https://vite.dev/guide/env-and-mode)

목표 경계는 `GameAPI -> LedgerRepository -> IndexedDB adapter | authenticated HTTP API`다. 온라인 모드에서는 브라우저가 권위 장부를 직접 쓰지 않는다. 인증된 사용자 요청을 받은 서버 API가 권한·명령을 검증하고 서버 저장소에 쓴다. 먼저 로컬 싱글플레이에는 IndexedDB 어댑터를 붙이고, 계정/온라인 기능이 결정될 때 동일한 핵/명령 계약 뒤에 서버 저장소를 추가한다. 이 저장 어댑터와 계정별 분리는 아직 구현되지 않았다.
## 대규모 온라인 게임에서 참고할 저장 구조

이 프로젝트의 “장부 하나”는 논리적 권위 모델을 뜻한다. 대규모 서비스에서 모든 유저와 월드 데이터를 한 파일이나 한 테이블에 몰아넣는다는 뜻은 아니다. 규모에 따라 계정, 캐릭터, 월드, 이벤트, 분석 데이터를 물리적으로 분리하고 ID와 API로 연결한다.

```text
클라이언트
  → 인증/게임 API
  → 권위 게임 서버(명령 검증, 월드 시뮬레이션)
  → 트랜잭션 저장소(계정/캐릭터/인벤토리/재화)
  → 이벤트·감사 로그 / 예약 작업 / 분석·운영 관측 파이프라인
```

- `account_id`는 로그인 계정을, `character_id`는 그 계정 아래 캐릭터를, `world_id`/`shard_id`는 공유 월드 분할을 식별한다. 개인 섬이면 소유 캐릭터 또는 계정 ID를 섬 소유자로 연결한다.
- 캐릭터의 현재 재화·인벤토리·장착 등은 빠르게 읽을 현재 상태로 저장한다. 코인 지급, 아이템 거래, 구매처럼 경제에 영향을 주는 중요한 명령은 서버에서 검증하고 원자적으로 갱신한다.
- 접속 중인 월드의 짧은 주기 위치/상호작용 상태는 권위 월드 서버 메모리에서 처리한다. 재접속·서버 복구가 필요한 상태는 주기적으로 스냅샷하거나 주요 변경 시 영구 저장한다. 모든 프레임을 DB에 쓰지 않는다.
- 도메인 이력은 구매·거래·보상·장착·월드 편집처럼 되짚거나 분쟁을 확인해야 하는 의미 있는 변경에 한정해 기록한다. 각 이벤트에는 이벤트 ID, 주체·대상 ID, 타입/버전, 기록 시각, 게임 효력 시각, 요청 중복 방지 키 등을 포함할 수 있다.
- 운영 로그(오류·지연·서버 상태)와 분석용 텔레메트리(플레이 행동 집계)는 유저 장부와 분리한다. 초당 대량의 위치/효과 이벤트를 전부 핵심 DB의 사용자 이력으로 남기지 않는다.
- 이벤트 이력에서 현재 상태를 전부 재구성하는 event sourcing은 선택적 고급 구조다. 이벤트와 현재 상태를 함께 저장할 경우 둘의 쓰기가 원자적이어야 하며, 스냅샷·버전 전환·재처리·중복 방지까지 설계해야 한다.

공개 사례에서 지속 월드는 접속 중 메모리 상태를 사용하고 복구·재접속을 위해 외부 저장소에 주기적으로 상태를 저장하는 접근이 설명되어 있다. AWS가 공개한 New World 사례는 월드 시뮬레이션을 여러 hub 서버로 분할하고, 게임 상태 저장과 분석 텔레메트리를 서로 다른 흐름으로 처리했다고 설명한다. 이는 특정 업체의 권장 제품을 채택하라는 뜻이 아니라 운영 책임을 분리하는 참고 사례다. [AWS: Persistent World Games](https://aws.amazon.com/blogs/gametech/host-persistent-world-games-on-amazon-gamelift-servers/), [AWS: New World Architecture](https://aws.amazon.com/blogs/gametech/the-unique-architecture-behind-amazon-games-seamless-mmo-new-world/)

이벤트 소싱은 이력/복구/감사에 유용하지만 설계·운영 복잡성을 높인다. 현재 상태 스냅샷은 이벤트 재생 비용을 줄이는 읽기 최적화이며 이벤트 원본과 구별한다. [Microsoft: Event Sourcing Pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)
## 현재 개발 범위: 로컬 싱글플레이만

초기 플레이 저장은 한 브라우저 프로필의 한 로컬 세이브 슬롯으로 제한한다. 브라우저 IndexedDB의 고정 논리 이름을 사용하고, 저장 파일의 OS 경로·유저 계정 서버·멀티플레이 월드·기기 간 동기화는 현재 범위에서 다루지 않는다. 브라우저가 실제 저장 경로를 관리한다. API 뒤에 저장 어댑터를 두므로 추후 온라인을 결정하면 같은 명령 모델 뒤에 서버 어댑터를 추가할 수 있다.

현재 코드는 아직 IndexedDB 어댑터를 연결하지 않아 라이브 세션 메모리에만 저장한다. 싱글플레이 저장을 구현할 때의 첫 목표는 `02_api-controller`에서 IndexedDB 어댑터를 조립하고, 실행 시작 시 세이브를 읽고, API 명령 성공 뒤 장부 스냅샷을 저장하는 것이다. 저장 실패 표시와 JSON 백업은 그 구현에서 함께 고려한다.

# 콘텐츠 등록 형식

## 원칙

새 콘텐츠는 기존 게임 시스템이 읽는 데이터와 에셋을 추가해 등록한다. 특정 아이템 ID를 UI나 월드 코드의 조건문에 직접 넣지 않는다.

## 의상 정의 예시

```ts
interface ClothingDefinition {
  id: string
  displayName: string
  slot: ClothingSlot
  asset: string
  icon: string
  compatibleRigIds: string[]
  rarity: ItemRarity
  unlockRule?: UnlockRule
}
```

실제 타입과 현재 장부 데이터는 `src/01_nucleus-core/`에서 소유한다. 그래픽·UI는 API 경계를 거쳐 장부 스냅샷을 받는다.

## 신규 의상 추가

1. 고유 ID를 정한다. 출시 후 ID를 변경하지 않는다.
2. 모델과 아이콘 에셋을 정해진 에셋 경로에 둔다.
3. 슬롯과 호환 리그를 선언해 카탈로그에 등록한다.
4. `npm run check:content`로 ID 중복과 경로 참조를 확인한다.
5. 커스터마이징 화면이 카탈로그를 통해 새 항목을 읽는지 확인한다.

## 게임 데이터 장부: 표 형태 JSON 워크북 제안

실제 XLSX 파일 대신, 장부와 시트(표)를 JSON 파일로 표현한다. 사람이 엑셀처럼 열과 행을 이해할 수 있고, 코드가 스키마를 검사해 게임 런타임에서 안전하게 읽도록 하는 구조다.

이 장부는 정적 콘텐츠 카탈로그에 그치지 않는다. 캐릭터 생성, 아이템 획득·장착, 재화, 맵 배치와 같은 게임 진행 상태도 기록하는 게임의 권위 데이터 모델이다. 화면이나 3D 객체는 장부의 내용을 보여주는 인스턴스다.

### 파일 구조 제안

```text
game-data/
  workbook.json          장부 형식 버전과 시트 목록
  sheets/
    characters.json      캐릭터 정의/플레이어 캐릭터 상태 표 또는 역할별 분리 시트
    clothing.json        의상 표
    maps.json            맵 표
    tiles.json           타일 표
    objects.json         3D 오브젝트 표
    assets.json          에셋 ID와 파일 경로 표
    ui-elements.json     데이터로 구성할 UI 프리셋 표 (필요할 때)
    inventory.json       플레이어 보유 아이템 상태
    progression.json     재화·경험치·진행 상태
    placements.json      플레이어 월드 배치 상태
```

각 시트는 열 정의와 행 목록을 가진다. 행은 열 키를 가진 객체로 저장해 AI가 열 순서에 의존하지 않게 한다.

```json
{
  "sheetId": "clothing",
  "schemaVersion": 1,
  "columns": [
    { "key": "id", "type": "string", "required": true },
    { "key": "displayName", "type": "string", "required": true },
    { "key": "slot", "type": "enum", "required": true },
    { "key": "assetId", "type": "reference", "required": true },
    { "key": "rarity", "type": "enum", "required": true }
  ],
  "rows": [
    {
      "id": "cloth.sky-beret-001",
      "displayName": "구름 베레모",
      "slot": "head",
      "assetId": "asset.sky-beret-model",
      "rarity": "rare"
    }
  ]
}
```

이 형식은 실제로는 JSON이지만 열과 행을 가진 테이블로 취급한다. 열 정의가 행의 허용 필드와 타입을 결정한다. 필요하면 엑셀에서 익숙한 좌표 표기는 문서·편집 도구에서 계산해 표시할 수 있고, 저장 데이터 자체에는 반복적이고 깨지기 쉬운 셀 위치를 쓰지 않는다.

### 참조와 조립

- 각 행은 변경되지 않는 고유 ID를 가진다.
- 의상은 `assetId`, `slot`, `compatibleRigIds`로 모델 에셋과 장착 규칙을 연결한다.
- 맵 타일은 `mapId`, 좌표, 레이어, `tileId`를 행으로 가져 맵 배치를 표현할 수 있다.
- 오브젝트는 R3F에서 이미 구현된 `componentType` 또는 `prefabId`를 참조한다.
- 캐릭터 프리셋은 베이스 리그 ID와 초기 외형·장착 아이템 ID를 참조한다.
- 에셋은 시트에서 ID와 경로를 매핑하고, 다른 표에서는 파일 경로 대신 에셋 ID를 참조한다.
- UI의 버튼이나 패널 자체는 React 컴포넌트로 구현한다. 장부에는 데이터 기반으로 조립할 필요가 있는 화면 프리셋과 설정만 기록한다.

### 데이터 장부와 코드의 경계

- 장부는 **무엇이 존재하고 어떤 값·에셋·컴포넌트에 연결되는지** 설명한다.
- 구현 코드는 **그 콘텐츠가 어떻게 렌더링되고 동작하는지** 정의한다.
- `componentType`은 등록된 R3F/React 구현만 선택한다. 장부 안에 임의의 JavaScript 코드나 실행 문자열을 저장해 실행하지 않는다.
- 기존 규칙으로 표현되는 새 옷·타일·오브젝트는 장부 행과 에셋을 추가해 등록한다.
- 새로운 행동이나 규칙이 필요하면 런타임 시스템을 한 번 확장하고, 장부 스키마와 검증 규칙도 함께 갱신한다.

## 장부를 중심으로 한 게임 진행

게임 규칙은 UI나 3D 엔진 없이도 장부만 읽고 쓸 수 있어야 한다.

```text
입력 -> 명령 -> 도메인 규칙 검증 -> 장부 쓰기 -> 장부 읽기 -> 화면/3D 인스턴스 갱신
```

예를 들어 사용자가 의상을 선택하면 UI는 `EquipClothing` 명령을 보낸다. 도메인 규칙은 아이템 보유 여부, 장착 슬롯, 리그 호환성을 검사하고 장부의 캐릭터 장착 상태를 갱신한다. 이후 UI와 R3F 캐릭터는 같은 장부 읽기 결과를 각자 화면에 반영한다. 장부만 조작하는 헤드리스 실행에서도 같은 규칙과 진행 결과를 얻어야 한다.

### 물리적 저장과 논리적 장부

- 런타임에서 장부는 타입이 있는 논리 데이터 모델이다. JSON은 장부를 파일로 내보내거나 정적 콘텐츠를 제공하는 직렬화 형식이 될 수 있다.
- 웹 브라우저는 배포된 정적 JSON 파일을 직접 수정할 수 없으므로, 싱글플레이 저장은 같은 시트 스키마를 사용하는 IndexedDB 어댑터에 기록하는 방안을 제안한다.
- 이 어댑터는 장부의 유일성 원칙을 바꾸지 않는다. 단일 플레이에서는 브라우저 저장, 향후 온라인에서는 서버 DB가 같은 논리 장부 인터페이스를 구현한다.
- 매 프레임의 카메라·애니메이션 같은 일시적인 표현 상태까지 영구 저장하지 않는다. 게임 규칙과 재접속에 영향을 주는 진행 상태를 장부에 기록한다.

### 필수 검증

- 시트 ID·형식 버전·열 키 중복
- 정의되지 않은 열, 필수 값 누락, 열 타입 오류
- 행 ID 중복과 시트 간 ID 참조 오류
- 존재하지 않는 에셋 파일, 허용되지 않은 경로
- 알 수 없는 슬롯·희귀도·컴포넌트 타입
- 맵 타일 좌표 중복 또는 범위 초과 (맵 형식 결정 후)

### 현재 구현 상태

- 이 워크북 구조와 장부 중심 진행 모델은 프로젝트가 지향할 데이터 설계안이다.
- 현재 `src/01_nucleus-core/ledger.ts`에 텍스트 시뮬레이션용 메모리 장부와 콘텐츠 정의가 있고, `src/02_api-controller/game-api.ts`가 외부 명령·질의 경계를 제공한다. 장부에는 구름섬과 오브젝트, 아바타, 성별 제한 없이 조합할 의상, 수집품, 설정, 미래 온라인 역할, 현재 상태·이력·예약이 함께 들어간다. 아직 직렬화 워크북이나 영구 저장 어댑터는 없다.
- 다음 단계에서 스키마 버전 정책과 표 형식 워크북을 정하고, 메모리 기반 `GameAPI`를 영구 저장 어댑터와 과거 시점 질의로 확장한다.
